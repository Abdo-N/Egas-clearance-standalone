Purpose and authority

The single Super Admin creates and maintains Admin accounts. It cannot manage operational users or clearance requests, and no account—including itself—can reset or delete the Super Admin.

Sole-account warning: there is exactly one Super Admin. The application has no self-service recovery path for it. Protect its credentials and establish an EGAS-approved recovery procedure before production use.

1. First-run setup and sign-in

Brand-new installation

When the database contains zero users, the login page redirects to the one-time setup screen. This is the only unauthenticated account-creation flow.

  1. Confirm that this is the intended new installation and that you are using the authorized server address.
  2. Enter the Super Admin holder’s full name, internal landline, work email, password, and confirmation.
  3. Use at least 12 characters with a symbol and follow any stronger EGAS password requirements.
  4. Submit once. As soon as any account exists, setup closes permanently and normal login begins.
  5. Create one or more Admin accounts so operational staffing can be provisioned.
Development reset: npm run seed:final:reset-users --prefix backend deliberately deletes every user to reopen setup. It is local/development-only and must never be used on production data.

Normal login screen after first-run setup is complete.

Sign-in security

There is no self-registration or emailed reset link. On an Admin's very first login, the password is the exact one the Super Admin entered when creating the account — it is already the Admin's real, permanent password, and the application does not force a change. A change is only forced if the Super Admin later issues a one-time password through Reset password (see section 3); only that flow forces a new permanent password before any other authenticated route can be used.

2. Create Admin accounts

Super Admin dashboard. Only Admin accounts appear because that is the Super Admin’s management boundary.

  1. Enter your current Super Admin password in the confirmation field.
  2. Enter the new Admin’s full name, internal landline, work email, and a strong password.
  3. Confirm the role is Admin; the interface does not offer operational or Super Admin roles.
  4. Review the exact email, create the account, and transmit the password securely.
  5. The Admin logs in directly with this password — it is already permanent, and the site does not force a change at first login — then creates File Management and reviewer accounts. If the Admin wants a different password later, they must ask you to reset the account, which does force a change on next login.

3. Reset or delete Admin accounts

Reset an Admin password

  1. Verify the Admin’s identity using EGAS policy and match the exact account email.
  2. Select Reset password, enter the Super Admin’s current password, and choose a temporary password.
  3. Transmit it through an approved secure channel. The Admin must replace it on next login.

Delete an Admin account

  1. Confirm departure/role change, the exact email, authorization, and that sufficient Admin coverage remains.
  2. Select Delete, read the permanent-action warning, and re-enter the Super Admin password.
  3. Confirm only when permanent account removal is intended.
Do not remove the last practical Admin coverage. Without an Admin, no one can create or maintain Document & Records Management or reviewer accounts until the Super Admin creates a replacement.

Neither action targets the current Super Admin account. This is enforced by the server, not merely hidden in the interface.

4. Lockout prevention and reference

Required operational safeguards

  • Keep the Super Admin email and credential in an EGAS-approved secure credential store.
  • Limit routine use; use Admin accounts for ordinary operational-account administration.
  • Keep contact details accurate so the login-page help flow is useful.
  • Maintain at least two authorized Admin accounts where policy permits.
  • Test the documented organizational recovery process in an isolated environment.
  • Never use the user-reset development command against production.
  • Log out after every Super Admin session and report suspicious access immediately.
